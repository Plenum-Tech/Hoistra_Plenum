## 2. Agent and service boundary

Hoistra is a property-management information, analysis and coordination platform for Property and Portfolio Managers, not the facility-management system that creates and operates work orders. Work orders are created and managed in a separate external system. Hoistra receives their status, summaries and source reports, reads/analyzes those records and inspection reports within authorized scope, and can prepare structured work-order requests and communicate them by permitted email. Sending a request does not create, assign, approve, dispatch, transition or close an operational work order; those operations are outside this platform, not future permissions implied for these roles. Report only external status actually supplied by the source; an email send or acknowledgement is not proof of work-order creation or progress.

The existing Plenum CAFM DeepAgent is the user-facing orchestration code being adapted. Its legacy tool inventory includes broader facility-management operations that are not active product requirements or permission grants. Only approved, verified adapters may be enabled. The intended property-management capabilities include:

- General database and entity queries, hybrid structured/document retrieval and graph relationships.
- Read/ingest externally supplied work-order reports and status summaries; analyze maintenance/SLA findings and inspection reports; prepare structured email requests without operating the external work-order lifecycle.
- Spreadsheet migration, live Fiix mapping/sync, source connector tests and ingestion batches.
- Document indexing, extraction, cited search, metadata and immutable evidence/version retention; original-source deletion is prohibited by DOC-02.
- Compliance certificates, taxonomy, coverage, verification, renewals, approvals and evidence.
- Contract extraction, criticality, vendor scoring, invoices/adversary checks and approvals.
- Energy readings, gaps, benchmarks, condition, anomalies, recommendations and reports.
- Planning, delegation, session memory/files, stateless/stateful/streaming APIs and error reporting.

### 3.1 Role definitions and ordinary data scope

| Role | Code identifier | Ordinary data scope |
|---|---|---|
| General User | `general_user` | One assigned building or an assigned portfolio of buildings |
| Portfolio Manager | `portfolio_manager` | Buildings within their assigned portfolio |
| Property Manager | `property_manager` | Their single assigned building |

Seeing a vendor certificate means evidence relevant to the user's permitted buildings/portfolio; the exact vendor-to-building relationship must be defined in fixtures and enforced in queries. A vendor existing in the same organization does not automatically make every vendor record visible to every role.

General Users' no-write rule applies to business records. Generating/sending their permitted email is an explicit exception, including the technical email draft/send/audit records needed to execute it. It does not authorize changes to the underlying work order, asset or certificate. Likewise, a manager's add/ingest grant and vendor-block grant do not confer general edit permission.

Controlled derived corrections are not general editing rights. Show original evidence, the current value, proposed value and reason. Any one eligible person may explicitly approve and apply the correction, including its proposer. Preserve original sources and before/after values, and resolve the proposal atomically to prevent duplicate application. General editing, source modification and deletion remain ungranted or prohibited; apply CORR-01 through CORR-08 and the applicable role/function scope.

Adding a building does not confer organization creation or unrestricted assignment administration. It must stay within the Portfolio Manager's assigned portfolio. Only Portfolio Managers add buildings; Property Managers do not.

### 3.3 Organization-wide vendor blocking

Vendor blocking is an explicit exception to a manager's usual building/portfolio data scope: an authorized Portfolio Manager, Property Manager or Compliance Officer can block a vendor in their own organization, and that block prevents new work-order requests to that vendor across the organization. It does not apply to other organizations. A General User cannot block a vendor.

A blocking grant does not authorize arbitrary updates to vendor records or grant visibility into other buildings. Section 3.11 defines eligible vendor links, reason/evidence, explicit confirmation, audit and preservation of existing work orders. Compliance Officer authority is restricted to certificate management and expiry-related blocking/unblocking. Section 3.6 defines the approved evidence-backed unblocking exception. Do not silently cancel or close existing work orders when blocking a vendor. This specification grants prevention of new requests, not changes to existing jobs.

### 3.4 Identity and backend enforcement

The server must obtain the caller's identity, role and assignments from an authenticated session and trusted application data. User messages, `context`, supplied organization IDs, `lookup_user` results selected by the model and session IDs are not proof of caller identity or authority.

Every read, document retrieval, aggregate, export and write must enforce the caller's capability and organization/scope before returning restricted information or changing state. UI hiding, tool registration and the system prompt cannot replace backend authorization. Multi-step workflows must check the actual downstream effects: an allowed ingestion action must not become an unauthorized overwrite, record edit, workflow dispatch or connector-administration action.

The active isolated homework endpoints establish a trusted test principal through the private server-owned session fixtures. Points 1/2 verify scoped read and audit enforcement. Legacy workflow, specialist, stateful/resume and streaming paths remain blocked in homework mode; they must not be treated as authenticated/authorized merely because the new homework routes are protected. Production identity wiring and unenabled domain/action adapters remain implementation work. Read authorization tests are no longer blocked; their evidence applies only to the tested read profile.

### 3.6 Approved action, confirmation, approval and refusal boundaries

These decisions were explicitly confirmed by the owner after v0.2.0. They supersede conflicting earlier proposals; they do not claim that the running code enforces them.

- **ACT-01 — Source immutability:** raw incoming/instrumented data, original source documents and original ingestion reports remain immutable. Corrections to derived application records require separate authority and the applicable approval; approval does not authorize rewriting source evidence.
- **ACT-02 — Equal certificate authority:** Compliance Officers, Property Managers and Portfolio Managers can approve and execute derived certificate corrections, building certificate renewal/inspection bookings and vendor-accreditation renewal. Compliance Officers cover their organization; Property Managers their assigned building; Portfolio Managers their assigned portfolio and relevant vendors. No Compliance Officer countersignature is required solely because the actor is a manager.
- **ACT-03 — Vendor block authority:** all three roles have equal approval/execution power for vendors eligible under their assignment and function scope. Compliance Officer power is limited to certificate-expiry-related actions as defined in VENDOR-02. Every approved vendor block has organization-wide effect within their own organization. This exception does not grant unrestricted access to other buildings' information.
- **ACT-04 — Evidence-backed unblocking:** a renewed certificate triggers verification and a proposed unblock, not automatic reinstatement. Check all outstanding blocking reasons and preserve the evidence. The vendor remains blocked until an authorized one of the three roles approves. Approval/execution has organization-wide effect and records actor, evidence, reason, decision and time. This replaces the earlier blanket refusal of user-requested unblocking; arbitrary or unsupported unblocking is still refused.
- **ACT-05 — User-requested email:** show recipients, subject, body and attachments and obtain confirmation before sending. Booking approval must clearly disclose any combined email send (for example “Approve booking and send this email”); generic approval must not hide a send. Enforce the role's permitted recipients, data scope and purpose. Confirmation cannot grant otherwise missing permission.
- **ACT-06 — Automatic notifications:** routine informational notifications and escalations may run automatically through configured rules and recipients. They do not approve business changes. Keep actual send/handoff/failure status and audit records distinct; avoid duplicate sends and blind retries of unknown delivery outcomes.
- **ACT-07 — Certificate action window:** use 30 days or fewer, inclusive. Proposed bands approved by the owner: 8–30 days action-required; 1–7 critical; day 0 “expires today” for both building and vendor certificates; negative days expired. Above 30 follows existing advance reminders. Missing expiry is unknown unless a documented review-date rule applies. Detection/notification may be automatic; the resulting business action still follows role/approval rules. The reviewed vendor day-zero rule conflicts and must be changed in code before conformance can be claimed.

**Approved implementation reconciliation — expiry terminology (2026-10-25):** retain ACT-07 unchanged. Use the same expiry labels in building/vendor certificate tools, skills, filters, counts and responses: 8–30 days inclusive is action-required; 1–7 is critical; day 0 is “expires today”; negative days are expired/lapsed; missing expiry is unknown unless an applicable documented review date supplies the anchor. Preserve existing advance reminders above 30 days, clearly separated from the inclusive 30-day action window. Reconcile `skills/compliance/tool-routing.md`, related vocabulary/renewal/answering instructions and the operations `compute_certificate_status()` / `vendor_risk_level()` paths; day zero must not be displayed as expired/lapsed or merely hidden under a generic critical label. Keep expiry classification, vendor risk and approved vendor block state distinct: date classification alone must not silently change vendor eligibility. Verify matching row/count filters and boundaries at 31, 30, 8, 7, 1, 0 and -1 days, plus missing expiry and documented review-date fallback, for both building and vendor certificates. These are required implementation changes before domain enablement; this specification update does not implement or certify them.

- **ACT-08 — Single authorized person approval (OPEN-02 resolved):** any person whose role and scope authorize the action may propose, explicitly approve and execute it. Self-approval is allowed; no different reviewer, higher role or countersignature is required. This includes evidence-backed vendor unblocking and permitted derived-record corrections. Renewal alone still does not unblock a vendor: explicit approval is required, and the vendor remains blocked until then. Corrections preserve original evidence and before/after values; both actions retain actor, decision, time and evidence in the audit trail. A draft, tool suggestion or model-generated approval is not the human decision. No special delegation workflow is required for this baseline: another person may act only under their own existing role and scope; chat cannot grant another person authority. Advanced temporary delegation and separation-of-duties workflows are outside baseline scope.
- **REFUSE-01 — Prohibited mutations:** refuse changes to source work-order records or original ingestion reports, deletion of hoisted buildings and mutation of raw/instrumented/incoming source data. Supported derived corrections are a separate controlled process; they do not waive these refusals.
- **REFUSE-02 — Scope:** refuse requests outside the caller's assigned building/portfolio or organization, except for explicitly granted functions: organization-wide compliance access for Compliance Officers, eligible organization-wide vendor block/unblock effects, and own-organization vendor-scoring configuration administration for Portfolio Managers under SCORE-ADMIN-01. Each exception applies only to its stated function and never crosses organization boundaries. Scoring administration does not grant access to other portfolios' restricted records, invoices, reports or individual performance results.

Email delivery is resolved for Homework 1 by the simulated outbox in Section 3.12; real email integration is deferred. Other remaining decisions are listed in Section 3.5. Correction and vendor eligibility rules are resolved for the homework baseline in Sections 3.10–3.11. The manager approval grants below reconcile the owner’s earlier approval of the specific manager permissions; they are not additional general editing or work-order-management permissions. Do not promote earlier recommendations on those subjects to approved policy. Existing approval/scan/edit tools contain effects that conflict with these requirements; approval workflows require backend enforcement, not only prompt wording.

### 3.13 Approved broader HOI Score — fixed Homework 1 fixtures

Owner approved ten equal-weight groups, required-field checklist and fixed expected quantities on 2026-10-25. Formula identifier: `hoi-fixed-coverage-v1`. This supersedes the nine-field `record-completeness-v1` choice from specification v0.10.0; preserve that older baseline as historical evidence. The unapproved six-category suggestion is not used.

HOI Score measures populated required fields across expected building records, not compliance, record accuracy, safety, condition or performance. The following target quantities apply to **each fictional Homework 1 test building**, not to real-world statutory obligations. Define stable expected item IDs in setup fixtures before runs; the model cannot alter targets, required fields, applicability or weights to raise the score.

| Group (10% each) | Fixed expected items per building | Required fields |
|---|---|---|
| 1. Building and locations | 1 building profile; 2 locations | Profile: name, country, city/region, building type, floor count, floor area with unit. Location: name, type, parent building/location. |
| 2. Assets | 5 asset records | Asset reference, name, category/type, assigned location, operational status. |
| 3. Maintenance | 3 externally created work-order report records; 2 externally supplied PPM schedules | WO: reference, asset/location, issue description, raised date, status. PPM: reference, asset/location, maintenance task, frequency, next due date. |
| 4. Inspections | 2 inspection reports | Report reference, inspection type, inspection date, inspected building/asset, findings/result. |
| 5. Compliance | 3 building certificates; 2 vendor accreditations | Certificate reference/number, certificate type, building/vendor holder, issuer, issue date, expiry or applicable review date. |
| 6. Vendors and contracts | 2 vendors; 2 contracts | Vendor: reference, name, trade/service, contact. Contract: reference, vendor, effective dates, service scope, stated SLA targets and applicable rates. |
| 7. Invoices and commercial records | 2 invoices, each with 2 lines; 1 purchase order | Invoice header: reference, vendor, date, total/currency. Line: description, quantity, unit price, line amount. PO: reference, supplier, date, status, total/currency. |
| 8. Energy and metering | 2 meters, each with 4 timestamped readings; 1 building energy profile | Meter: reference, type/fuel, building/asset. Reading: meter reference, timestamp, consumption value, unit, interval. Profile: building type, floor area and unit. |
| 9. Parts and resources | 3 spare-part records; 2 resource assignments | Part: reference, description, stock location, quantity, unit. Assignment: resource reference, role/trade, assigned building/team. |
| 10. Supporting documents | 1 manual; 1 drawing; 1 warranty | Document reference/title, type, linked building/asset, version or issue date, accessible processed content. |

**HOI-01 — Eligibility and fields:** a record must be successfully ingested, accepted and linked to the correct building/relevant entity before it earns field credit. Accepted incomplete records can earn partial credit. Preserve source references and audit metadata but do not award points merely for generated IDs or audit timestamps. Business references identified in the table must come from source evidence or an approved correction. A known meaningful zero counts; blanks, unknowns, failed extraction, invented values and platform-default-filled guesses do not count as supplied evidence.

Compound labels such as total/currency, area/unit and effective dates require all components specified in the fixture field list. For SLA targets, rates, issue/expiry/review dates and document versions, setup fixtures declare source-applicable fields before testing. Do not require a fact the source legitimately does not contain; do not let the agent dynamically mark a missing expected field inapplicable. The baseline keeps all ten groups applicable and uses the fixed quantities above.

**HOI-02 — Deterministic hierarchy:** calculate unrounded fractions until the final score:

1. Record completeness = populated required source-supported fields / applicable required fields from its fixed checklist. A missing expected record scores zero. Unexpected extra records do not fill an expected slot without a verified identity match.
2. Record-type completeness = average completeness across that type's fixed expected records (including missing records as zero).
3. Group completeness = equal average across its record types, not a raw count of all rows. Building/profile and locations are two types; maintenance WO/PPM are two; compliance building/vendor certificates are two; vendors/contracts are two; commercial invoices/POs are two; energy meters/readings/profile are three; parts/resources are two; supporting manuals/drawings/warranties are three. Assets and inspections each have one type.
4. Each invoice's completeness = equal average of its header completeness and the average completeness of its two expected lines; then average the two invoice scores. For energy, average all eight expected readings for the reading type, all two meters for the meter type, and the one profile for the profile type. Expected timestamps/intervals are fixed by fixtures, not expanded by runtime date.
5. HOI Score = 100 × average completeness of the ten groups. Round only the final result to the nearest whole percentage, with .5 rounded upward. Each group can contribute at most 10 percentage points. No dynamic reweighting or guessed denominators.

**HOI-03 — Examples:** ten complete groups = 100%; five complete and five empty groups = 50%. If 3 of 5 expected assets are complete and 2 are absent, asset completeness is 60% and contributes 6 points. One complete invoice with its two lines, one absent invoice, and one complete PO gives commercial completeness (50% + 100%) / 2 = 75%, contributing 7.5 points before final rounding.

**HOI-04 — Duplicates and overlap:** duplicate files/records cannot earn extra credit. A document shared across buildings requires independently authorized links. Certificate/inspection evidence earns credit in its own group and cannot also fill a supporting-document slot. An invoice line is scored only through its invoice as described above. More uploads or lines cannot inflate a capped record/type/group score.

**HOI-05 — Conflicts and versions:** preserve accepted values pending the approved correction process. Conflicting proposed/unapproved values earn no new credit; accepted existing values remain credited. Preserve both source versions when replacing evidence and count the selected current representation once. Expired certificates and failed inspection results can still be complete evidence; compliance/condition is assessed separately.

**HOI-06 — Explainability and role-scoped visibility:** only Property Managers and Portfolio Managers may view the HOI Score, ten-group breakdown, missing-category/item/field details and permitted supporting evidence. Property Managers are limited to their assigned building; Portfolio Managers to assigned portfolio buildings. Organization-wide vendor-scoring administration under SCORE-ADMIN-01 does not expand HOI/building-data visibility. General Users and Compliance Officers may not receive even the overall HOI percentage by default; retain their already-permitted summaries and certificate evidence without exposing the cross-domain score or breakdown. Enforce this on tool/API responses, reports, links, attachments, notifications and drill-downs. Both assigned managers continue to receive the approved HOI recalculation/change-trail notifications. Stored score provenance includes formula ID, fixture checklist/version, accepted source records and calculation time. Missing fixture targets are a setup error; never fabricate a completeness score or substitute the legacy nine-field percentage. This policy records required enforcement; it does not enable a score tool or implement the scorer.

**HOI-07 — Existing update rules retained:** automatically recalculate after authorized data changes/approved corrections. Notify both assigned Property and Portfolio Managers through the simulated outbox with previous/new score (including unchanged results), additions/corrections, evidence, actor and formula version. Preserve history; no manual score setting or automatic permission/autonomy changes. Reuploading a duplicate cannot improve coverage.

**HOI-08 — Implementation gap:** the inspected code currently reads stored sites.hoist_score, computes a separate nine-field record_completeness_pct and displays the stored score. Neither is this approved ten-group formula. Implement the fixed fixture manifest, scorer, accepted-data/permission mapping, canonical API/UI/tool score, event history and simulated notifications; do not claim they already exist. Keep the nine-field measure separately named if retained, without substituting it for HOI Score. This specification update changes no runtime behavior.

**Approved implementation reconciliation — canonical HOI presentation (2026-10-25):** only the verified ten-group `hoi-fixed-coverage-v1` calculation may be labelled HOI Score. Return its formula version, calculation time and authorized completeness breakdown. Until that calculation is available, display “HOI Score not calculated”; do not substitute stored `sites.hoist_score` or nine-field `record_completeness_pct`. If retained, clearly label those as legacy values. HOI Score measures record completeness, not safety, compliance, condition or vendor performance. SCORE-ADMIN-01 vendor-scoring administration does not permit changing the HOI formula, expected quantities, field checklist or weights. Align domain skills, score adapters, API/UI presentation and provenance with this distinction before enabling canonical HOI reporting. This note records required changes only; it does not implement the scorer or alter runtime output.
